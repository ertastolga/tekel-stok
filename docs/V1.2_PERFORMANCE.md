# TekelStok V1.2 — Performance & Longevity Report (M11)

Plan reference: `docs/V1.2_MASTER_PLAN.md` §9 (methodology, targets), §5.6 (v6 "indexes only by
evidence"). Measured on 2026-10-08 at the M11 commit on branch `v1.2/professionalization`.

**Summary.** Every plan §9 target is met on the 100 000-sale / 3-year dataset, most by one to
two orders of magnitude. M11 found and fixed six longevity problems: costs that grew with
history, or plans that flipped once SQLite statistics exist. It also found one backup-hygiene
defect (D-25). Startup on the 3-year dataset fell from ~3.7 s to ~0.6 s. The "Kâr ve Maliyet
Kapsamı" tab fell from 2.2 s to 20 ms (30 days). All synthetic data and every measurement ran in
scratch folders; the owner's data was never touched (plan §2).

## 1. Method

### 1.1 Data (`app/tools/perf_dataset.py`, plan §9, M1f)
Generated through the **real services** (same code paths as the UI), seeded RNG, simulated
clock (`app.core.clock` seam). Each basket is auto-saved as a draft first, as Sepetli Satış
does. 2 % of baskets are parked and resumed (generator v2, M11).

| Dataset | Products | Days | Sales | Sale lines | Stock movements | Drafts | Receipts | Counts | File |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `10k`  | 10 000 | 365   | 10 000  | 29 665  | 40 417  | 5 906  | 56  | 4  | 19 MB |
| `100k` | 10 000 | 1 095 | 100 000 | 298 634 | 311 052 | 59 462 | 161 | 12 | 119 MB |

The sales mix is 60 % Sepetli / 40 % Hızlı, paid NAKİT / KART / unrecorded. Reversals are 1 %,
and 30 % of those are cross-day. Mal Kabul runs weekly with occasional estimated or free lines,
a 1 000-product count every 90 days, and monthly price changes. Popularity is Zipf-like.
Generation takes 34 s (10k) and 375 s (100k).

### 1.2 Measurement (`app/tools/benchmark.py`)
* Refuses to run unless `TEKEL_DATA_DIR` is a scratch folder outside `%LOCALAPPDATA%\TekelStok`,
  and refuses a `--veri` path inside the real data folder (tested). The given file is **never
  modified**; everything runs on a copy in the scratch folder.
* Clock pinned to the dataset's last business day 18:00, so Bugün / Son 30 Gün are full.
* `time.perf_counter_ns`, 2 warm-up calls, then N iterations: ≥ 200 for barcode resolve and
  checkout, 30 for interactive reads, 10 for heavy analytics, 1–3 for whole-file work.
  Reported as p50 / p95 / max. Analytics are measured **cold**, bypassing the facade cache.
  `analiz_onbellekli_genel` shows the cached path. Checkout runs on the real `CartService.checkout`
  path, one transaction per sale, `synchronous=FULL`.
* `--arayuz` also measures MainWindow construction, first refresh and first Analiz page open.
  This runs offscreen; modal startup prompts are auto-answered.
* `--v1-bicimi` first rebuilds the copy on the **V1.1 schema (v1)**: v1 tables, v1 columns,
  version stamp 1. The first open then measures the real **V1.1 → V1.2 upgrade** at 100k scale,
  including the pre-migration backup.
* The `PRAGMA optimize` that runs on every close writes real planner statistics into these files,
  so later runs use the plans a long-running shop database would get (see §4.6).

Reproduce:
```
set TEKEL_DATA_DIR=C:\karalama\olcum
python -m app.tools.perf_dataset --hazir 100k --cikti C:\karalama\100k.db
python -m app.tools.benchmark --veri C:\karalama\100k.db --arayuz --cikti C:\karalama\rapor.json
python -m app.tools.benchmark --veri C:\karalama\100k.db --v1-bicimi
```

Intel Core i5-12500H laptop (12 cores), 15.7 GB RAM, NVMe SSD, Windows 11 Home 10.0.26200.

## 3. Startup decomposition (100k) and upgrade cost

| Step | Before M11 | After M11 |
|---|---:|---:|
| Open database (already current schema) | 2 ms | 3 ms |
| Shallow consistency check | **3 409 ms** | **376 ms** |
| Daily backup opportunity (first start of a business day with changes only) | 549 ms | 600 ms |
| MainWindow construction (lazy pages, M3c+) | 249 ms | 206 ms |
| First refresh | 25 ms | 18 ms |
| **Typical start** (no daily backup due) | **≈ 3.7 s** | **≈ 0.6 s** |

Page construction does not dominate, so no further lazy loading was needed (plan §7 M11).

**One-time upgrade.** A V1.1-shaped 100k database (schema v1) upgrades to v6 in **9.6 s** on
first start, including:
* the free-space precheck,
* the `guncelleme_oncesi_v1_v6_*.db` backup and its `quick_check` verification,
* five schema versions, each with a foreign-key check,
* the v6 index builds.

After the upgrade the shallow and deep checks both report **0 problems**, and the row counts
are unchanged. A v5→v6 upgrade (the earlier 100k file, which has the same generator but no drafts) takes 4.3 s. On the AVAPOS this one-time
wait is likely to be longer. The README (M12c) must tell the owner to expect it.

## 4. Findings and changes

### 4.1 Cost coverage ("Kâr ve Maliyet Kapsamı", §5.9) — 2.2 s → 20 ms
The M8a query computed two window functions over the **entire** movement history of every
product sold in the period. Its cost grew with the age of the shop, not with the length of the
period.

New query: for each sale line, two index lookups:
* the product's last pool reset before the sale (`ix_moves_pool_reset`, partial:
  `balance_after <= 0`),
* whether an unknown-cost inbound movement exists between that reset and the sale
  (`ix_moves_tainting`, partial).

Cost is now proportional to the period's sale lines. 100k: 30 days 2 198 → **20 ms**, 1 year
4 432 → **240 ms**.

Equivalence: the original query is kept in `tests/test_basarim.py` as an **oracle** and compared
row-for-row on random ledgers and generated datasets. Those ledgers include estimated, free
(bedelsiz) and known-cost receipts, counts to zero, same-day and cross-day reversals, and
receipt reversals. On the 100k file both queries return identical results for 30 days, 1 year
and all history.

### 4.2 Shallow startup check — 3.4 s → 0.38 s (same invariants)
* I1 / I2 / I28 (product cache ↔ ledger totals) aggregated `stock_movements` in index order, which
  means one random page read per row. `NOT INDEXED` makes it a sequential pass:
  1.2 s → 0.13 s each, identical result.
* I21 / I22 / I25 / I26 (single-row checks on sales and movements) are bounded to the last
  30 days in shallow mode, like the existing sales checks. The deep check still scans all history.
* I17 / I18 / I29 / I30 (count lines) are bounded the same way, by count sessions committed in the
  last 30 days or still open, through the session index.
* The red proof against HEAD `f990c82` lists the full-history scans this removed.

### 4.3 Deep check — 6.0 s → 2.1 s
I24 (running balance) used a window function **self-joined** back to the table. It is now a
single sequential pass (`NOT INDEXED`), with the same comparison.

### 4.4 Support package — 16.2 s → 7.4 s
The package ran both `PRAGMA quick_check` (Sistem Durumu row) and the full `integrity_check`,
which already covers `quick_check`. The status row now shows the full check's result
("Tam bütünlük denetimi"). The remaining time is `integrity_check` plus the deep check:
O(file size), on an explicit, rare action.

### 4.5 Growing tables nobody measured
* **Basket drafts.** Every auto-saved basket stays in `cart_drafts` as CHECKED_OUT, one row per
  Sepetli sale (59 462 rows at 100k). The perf generator did not model this before M11.
  Changes:
  * The "Müşteri n" counter (`ORDER BY id DESC LIMIT 200` backward scan) now reads only drafts
    parked in the last 36 h, through `ix_cart_drafts_parked`.
  * Open-draft queries use the always-small partial index `ix_cart_drafts_acik`
    (`WHERE status = 'OPEN'`).
  * Draft lines are found by `ix_cart_draft_lines_draft`.
* **Count baselines (I27).** For every product initialised by a count, I27 looks up its baseline
  count line. Without statistics (a fresh install) SQLite scanned **all** count lines per product.
  Fixed with `ix_count_lines_product`.

### 4.6 Plans that flip once statistics exist
`PRAGMA optimize` runs on every close and writes `sqlite_stat1`. That changed two plans for the
worse:
* **Cost coverage.** The planner picked the general `(product, id)` index for the reset lookup:
  30 days 18 → 184 ms, 1 year 0.25 → 2.1 s. The two partial indexes are now pinned with
  `INDEXED BY`; migration v6 guarantees they exist.
* **Parked-basket count.** The `(status, kind)` statistics showed every row CHECKED_OUT, so the
  planner scanned the whole index to count the OPEN rows. Fixed by the OPEN-only partial index.

The plan guard now replays the **real statistics captured from the 100k file**, so plan flips
like these are caught deterministically in the default suite (§5).

### 4.7 D-25 — backups left two orphan files each
The backup API copies the live database's WAL header. Every read-only verification of a backup
(`inspect`, pre-migration verification) therefore created `-wal` and `-shm` files it could not
delete. Retention deleted only the `.db`, so two orphans per backup accumulated forever.

Fix:
* Backups are written as single rollback-journal files (`journal_mode=DELETE`, +16 ms).
* Retention also removes a deleted backup's leftover side files from earlier versions.
* Restore already switches the restored data back to WAL when it opens it.

Red → green in `tests/test_yedek_motoru.py`.

## 5. Schema v6 and the deterministic guards

**v6 (index-only, no data change, append-only):** `ix_moves_pool_reset`, `ix_moves_tainting`,
`ix_cart_drafts_acik`, `ix_cart_drafts_parked`, `ix_cart_draft_lines_draft`,
`ix_count_lines_product`. Each is backed by a measurement or a plan proof above.

Write cost: checkout p50 stays at 3.5–4.1 ms. The two `stock_movements` indexes are partial and
hold only resets and unknown-cost inbound movements.

**Default suite (deterministic, plan §9):**
* `tests/test_sorgu_planlari.py` runs 18 hot operations through the real services:
  * KASA: resolve, Ürün Ara, add, checkout with auto-save, Hızlı Satış, undo last sale,
    park/resume.
  * YÖNETİM: product list, price list, category tree, recent sales.
  * Every Analiz tab, and the startup check.

  It captures the SQL actually executed (`set_trace_callback`) and fails on any **full pass**
  (`SCAN`, with or without an index) over a table that grows with sales. It runs once without
  statistics and once with the captured production statistics. Exceptions are listed with
  reasons, and a test fails if an exception is no longer used:
  * backward rowid scans that stop at `LIMIT`,
  * the deliberate sequential ledger totals,
  * the reversal-only partial index used by I31.

  It also asserts the v6 indexes exist on new installs and after the V1.1 fixture upgrade.
* `tests/test_basarim.py`: oracle equivalence (§4.1); the benchmark tool end-to-end on a small
  dataset; the V1.1-shape conversion upgrades cleanly; refusal of a missing scratch folder or real
  data.
* Limitation: a full pass hidden inside an index *range* (for example "all history of one product
  via `ix_moves_product`") is not a `SCAN` and is not flagged. The wall-clock benchmarks cover
  that case; §4.1 was found that way.

**`-m perf`:** `test_plan_hedefleri[10k|100k]` runs the benchmark on the cached templates and
asserts every target in `HEDEFLER_MS` (p50). If a target misses, the run is repeated **once**
(documented retry); a second miss fails, never a silent relaxation. Also included: template
integrity and deep invariants.
