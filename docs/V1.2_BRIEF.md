# TekelStok V1.2 — Professionalization Master Program

You are working on the existing TekelStok Windows desktop POS/inventory application.

This is a substantial V1.2 professionalization program.

The current V1.1 Sales-First POS implementation is the stable baseline. It has already passed a release-candidate audit, full tests, self-test, frozen Windows build verification, payment-safety checks, customer-display failure checks, checkout state-machine checks, and analytics checks.

The goal of V1.2 is NOT to rewrite the application.

The goal is to evolve TekelStok from a working small-shop POS into a much more polished, ergonomic, configurable and commercially credible retail management product while preserving the proven V1.1 accounting, inventory, barcode, backup and sales invariants.

======================================================================
EXECUTION MODEL — CRITICAL
======================================================================

This project must NOT become an interactive milestone-by-milestone process.

I want ONE comprehensive master plan first.

After I approve that master plan ONCE, you must execute the full approved V1.2 program autonomously.

You may internally divide the work into milestones/phases, but milestone completion is NOT a reason to stop and ask me for permission.

After approval, the default loop is:

1. implement the current internal milestone;
2. add or strengthen tests;
3. run targeted tests;
4. run the full regression suite;
5. fix regressions without weakening existing invariants;
6. commit a clean Git checkpoint;
7. update the V1.2 execution log;
8. automatically continue to the next internal milestone.

Do this repeatedly until the entire approved V1.2 scope is complete.

Do NOT ask:

"Milestone 2 is complete, should I continue?"

Do NOT stop merely because a phase completed.

Do NOT require routine product decisions from me if a safe and sensible default can be inferred.

Record such decisions in the execution log and continue.

======================================================================
ONLY STOP AND ASK ME IF
======================================================================

Stop only when at least one of these is genuinely true:

- continuing may cause irreversible user-data loss;
- a destructive or ambiguous database migration is required and the correct data semantics cannot safely be inferred;
- two requirements materially contradict each other;
- a decision would fundamentally change the product's long-term architecture and there is no clearly safer default;
- a required external hardware/protocol fact is unknowable from the repository;
- the V1.1 baseline itself turns out to be unexpectedly broken;
- a proven accounting/inventory/barcode/backup invariant would have to be abandoned;
- a security-sensitive decision cannot be implemented safely without owner input.

Routine matters such as:
- UI spacing,
- names of internal classes,
- small indexes,
- test organization,
- minor dialog wording,
- internal file structure,
- implementation details

are NOT stop conditions.

======================================================================
PRODUCT PRINCIPLE
======================================================================

TekelStok serves two fundamentally different workflows.

1. KASA / DAILY POS

This must remain extremely simple.

Primary workflow:

scan products
→ basket
→ NAKİT or KART
→ next customer

The cashier workflow must remain touch-first, fast, non-modal wherever possible, and suitable for an older or non-technical shop owner.

Management functionality must NOT make daily checkout more complicated.

2. YÖNETİM / MANAGEMENT

This may contain the powerful functionality:

- products;
- categories;
- bulk editing;
- inventory;
- purchases;
- prices;
- analytics;
- settings;
- backup;
- diagnostics;
- administration.

The conceptual separation between KASA and YÖNETİM should become clearer in V1.2.

======================================================================
I — MANAGEMENT PROTECTION
======================================================================

Add a lightweight Manager PIN boundary for sensitive management functions.

This is a locally administered shop application, not enterprise identity management.

Daily sales must NEVER require a manager PIN.

Candidate protected actions:

- Settings;
- bulk price changes;
- backup restore;
- sensitive product deactivation;
- sensitive historical corrections;
- other clearly destructive management actions.

Do not over-protect harmless navigation.

Do NOT store the PIN in plain text.

Use an appropriate salted password/PIN derivation scheme available in the existing Python environment or a carefully justified dependency.

Design a local owner recovery/reset process that does not create a dangerous backdoor.

Document the threat model honestly:

the goal is preventing accidental/unauthorized shop-floor changes, not defending against an administrator with full access to the Windows machine and database files.
